# 房间生命周期与计分同步检查（2026-10-12）

## 检查结论与产品选择

不用删除闲置房间来判断在线人数。房间是否允许继续记分、玩家是否正在使用房间、历史战绩是否保留，是三个不同状态。

采用以下策略：

- 在线依据：前台房间会话每 30 秒发送心跳，最近 90 秒内有心跳且未主动退出才算在线。切后台停止轮询与心跳；房间内的辅助算分、规则配置、历史页仍属于该会话。
- 首页：缓存不展示旧在线人数，刷新后无人房间显示“暂无人在房间”；首页停留期间每 30 秒刷新。
- 关房：无人后保留 5 分钟返回窗口，定时任务每 5 分钟扫描。主动最后一人退出可立即开始窗口；直接关闭微信或断网则在 90 秒心跳过期后开始窗口。实际归档时间还受下一次定时器执行影响。
- 有有效心跳时，即使 30 分钟没有记分也不关房。30 分钟无活动保留为兼容兜底，关闭前仍复核在线与最新房间活动。
- 归档仅将 `status` 改为 `finished`，保留玩家、计分、规则与战绩，清理二维码文件。不会删除业务数据。

## 已定位并修改的问题

| 问题 | 原因 | 修改 |
| --- | --- | --- |
| 记了一段时间后各端不同步 | `getRounds()` 单次查询无分页；同步合并又保留本地已确认记录。查询截断后各端只积累自己提交的新记录 | 新增授权云函数 `getRoomSnapshot`，按固定最大序号分页读取完整记录；首页进入、同步、历史总结算共用这一读取路径 |
| 不知道何时同步断了 | 轮询异常被静默忽略 | 显示重连状态，失败后继续重试 |
| 旧请求覆盖新数据 | `setInterval` 请求可能重叠；停用后又启动时共享布尔标记无法识别旧请求 | 串行轮询、会话令牌、切后台暂停及前台恢复 |
| 本地记录和服务端确认重复计分 | 轮询先拿到真实记录时，确认回调可能再添加一次 | 按真实 `_id` 和操作编号去重替换 |
| 长期假在线 | `isOnline` 只在主动退出时修改 | 心跳租约，显式退出仍立即离线 |
| 闲置扫描不完整及误关竞争 | 固定扫描前 100 房间；旧快照关闭前未复核；云环境写死；二维码清理未等待 | 全量分页扫描、事务复核、动态环境、等待清理、隔离单房间失败 |
| 微信身份读取错误 | 云函数读取小写 `openid`，SDK 字段实际为 `OPENID` | 修正字段；新记录绑定真实身份；旧空身份记录通过原设备 `clientId` 恢复并绑定 |
| 手动计分可伪造他人扣分 | 未检查调用者拥有哪个玩家；金额可为字符串或非有限数字 | 云端校验调用者身份，只能扣自己的分，必须安全整数且总和为零 |
| 并发序号重复、并发重复提交 | 先查最后一笔再添加；幂等查询在写入前独立执行 | 房间序号计数器、确定性操作文档 ID、事务原子写入；旧房间序号取已有最大值作为迁移种子 |
| 创建房间/入房破坏旧战绩 | 达到展示限制时直接删除旧玩家记录 | 删除这一清理逻辑；展示最多十场不影响数据库历史 |
| 加入/关房竞争或并发重复加入 | 判断房间后分步写入 | 事务复核状态；新玩家按房间和 OPENID 使用确定性 ID；旧玩家保留原 ID |
| 创建部分失败留下不完整房间 | 规则、房间、玩家分步创建 | 三类记录在事务中创建；确定性房间 ID 防止新版本并发使用同一房号 |
| 底分/规则更新异常 | 传入系统字段；非房主入口开放；恢复默认值没有真正删除自定义项 | 业务字段白名单、房主校验、移除可选字段、同步读取规则 |
| 多人买马不守恒 | 固定按三家分摊 | 根据实际非胡牌者人数计算；单人不转移分数 |
| 庄家倍数破坏杠分守恒 | 在全部胡分、杠分、马分完成后放大部分玩家总额；自摸可能使用残留点炮者 | 庄家倍数仅作用于胡牌转移，自摸忽略点炮者字段 |
| 云函数独立包代码漂移 | 各函数 `_shared` 副本与主版本不一致 | 新增 `npm run prepare:cloud` 和测试前一致性检查 |
| 错误后返回首页失败 | 对非 tabBar 首页调用 `switchTab` | 使用 `reLaunch` |

算分引擎所有语句、分支、函数及行覆盖率达到 100%。这不是整个项目 100% 覆盖。云函数测试使用内存数据库模拟原子提交与回滚，不代表已经验证微信云端 SDK 的实际冲突重试、网络、权限与定时器。

## 测试环境部署准备

1. 在项目根运行 `npm run prepare:cloud`，确保每个云函数的依赖模块已放入其目录。微信开发者工具应导入包含 `project.config.json` 的项目根，使用配置中的小程序及云函数路径。
2. 新增并部署 `getRoomSnapshot`；同步部署 `createRoom`、`joinRoom`、`settleRound`、`leaveRoom`、`getMyRooms`、`updatePlayer`、`updateRule`、`autoCloseTimeout`、`getRoomQRCode`、`logError`。每个函数安装自身依赖后上传，不能只上传 `index.js`。
3. `autoCloseTimeout/config.json` 已包含 `autoCloseTimer` 的 5 分钟定时配置。部署后检查云控制台是否实际存在并启用触发器，检查定时日志中的 `scanned`、`closed`、`failures`。仓库有配置不等于云端已生效。
4. 核验实际环境的数据库索引。主要查询包括：`rounds(roomId, roundIndex asc, _id asc)`、`rounds(roomId, roundIndex desc)`、`rounds(roomId, createdAt desc)`、`rounds(roomId, clientId)`、`players(roomId, _id asc)`、`players(roomId, isOnline, lastSeenAt)`、`players(openid)`、`players(clientId)`、`players(clientId, isOwner, joinedAt desc)`、`rooms(status, _id asc)` 和 `rooms(roomCode)`。按云控制台实际缺失索引提示建立，索引与权限不保存在当前仓库。
5. 核验数据库安全规则：业务读写由云函数授权后执行，不应允许客户端任意修改 `rooms`、`players`、`rounds`、`rules`。历史记录含 OPENID 或设备 ID，不能仅修改前端展示就认为访问权限已收紧。当前页面读取统一走授权快照，旧服务中尚有未被页面调用的直读接口。
6. 小程序前端与云函数需要配套验证。新身份校验对旧前端提交的空身份请求可能拒绝；不能将新云函数单独上线而不考虑在用的旧客户端。
7. 本次没有部署、发布、Git 提交或推送。生产动作需要用户明确指令。

## 真机验收

- 至少两台不同微信账号设备加入同一房间，交替给分超过 30 笔，逐笔检查双方总分、历史条数、总分守恒；建议继续到 121 笔以覆盖云端分页。冷启动重新加入后结果应相同，首页已结束战绩也应相同。
- 快速重复确认，以及两人同时给分，不得多扣；每个不同操作只记一次。模拟提交后立即断网，先检查历史再重复操作，因为网络超时不能证明服务端没有成功写入。
- 一台切后台或断网，另一台继续记分；恢复后应重连并补齐他人记录，后台不持续续在线租约。
- 全员主动退出后：首页应显示无人，在 5 分钟返回窗口后加上下次定时器扫描等待，房间归档，战绩可读；窗口内重入不应新建身份或丢分。
- 全员直接关闭微信：在心跳过期后显示无人，随后按无人窗口归档。至少一人前台停留 30 分钟但不记分，房间应保持可用。
- 房主修改底分/玩法项，其他设备刷新后读取相同规则；非房主不能改规则或他人昵称、不能替他人扣分。
- 老房间由原设备重新进入：昵称、玩家 ID 和历史关联保留；已归档的老房间可以查看战绩。

## 尚需现场核验的事项

- 无法从本地文件判断云端触发器是否部署、数据库安全规则是否正确，或此前真实运行的云函数版本是否与仓库一致。
- 过去已被旧逻辑删除的玩家记录，不能在缺少备份的情况下自动恢复。
- 当前同步采用每次完整分页读取，优先保证账目一致性。大型历史房间仍会增加云函数调用和读取成本，后续可基于事务序号改为增量同步；实际网络耗时与成本需要运行数据。
- 未使用的 `loginWithWx` 仍引用仓库中不存在的 `getOpenid` 云函数；当前页面未走这条登录链路，后续启用登录时必须重新设计，不能直接调用。

## 2026-10-13 真机反馈与修正

真机调试发现新玩家加入和首次记分时，读取尚不存在的文档触发 `document.get:fail ... does not exist`。核对实际使用的 `wx-server-sdk@2.6.3` 后确认，其默认行为为抛错，而此前内存模拟返回 null，未覆盖这一契约。

已为云函数数据库实例显式设置 `throwOnNotFound: false`，并修正测试模拟的默认行为，补充缺失文档与首次创建回归测试。前端云函数错误保留函数名、完整消息、错误码及可用的请求标识，避免丢失 SDK 普通错误对象中的信息。

本地 108 个测试通过，违规词及 diff 检查通过。用户反馈重新部署后的基本真机测试无明显问题，并授权提交当前版本；未提供每项验收的详细结果，不据此认定全部长时间、弱网及多人场景已经完成验收。推送仍需单独指令。
