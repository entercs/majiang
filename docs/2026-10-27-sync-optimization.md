# 同步与二维码优化部署说明

本次仅准备代码、规则和验证材料，没有部署云环境、修改套餐、提交或推送代码。

## 行为变化

- 创建房间默认底分为 1，直接打开邀请框，房间内入口名为“邀请”。
- 直接使用创建接口返回的二维码地址，创建阶段最多等待 1.2 秒预下载；等待超时继续进房，后台完成下载后仍可使用本地缓存。邀请框不等待完整房间资料才打开。
- 二维码图片加载前显示占位提示，自动重试一次；再次失败等待用户主动重试。关闭弹窗或页面卸载取消重试任务。下载缓存最多保留二十张。
- 记分响应丢失时先查询原操作，再用同一操作编号重试。仍不确定时保存在本机，阻止新的编号重复给分，退避自动核对并提供手动核对入口。结果确认后才显示成功。
- 记分明细、总分、序号和业务版本在同一事务内更新。新协议排行榜使用服务端已确认总分；未确认的临时记录不叠加到权威总分，避免重算。旧协议仍兼容。
- 旧房间首次访问时一次性分页补建总分，计分过程中发生并发变动则重新取数；摘要序号落后时会重新核对。不会删除或重编号旧记录。
- 房间初始化只取总分和最近一百条记录，用于近期变化提示。后续按游标补齐新增记录；没有变化时不查历史或规则。进入历史页才加载完整历史，期间新确认记录继续保留。
- 最终排行榜直接使用总分摘要，不再重读全部历史。
- 首页按最近十场批量查询，只查询活动房间在线人数；已结束房间不再逐个查在线人数。前端首页请求串行、隐藏后不更新页面。
- 清理任务优先处理 `nextCheckAt` 已到期的房间，并兼容缺少该字段的旧房间；每轮最多一百间、约二十秒处理预算，超出部分保留到下一轮。归档保留账目并发送关闭通知。
- 创建房间限频绑定真实微信账号，通过 `requestLimits` 原子记录控制，不能通过更换客户端编号绕过。
- 相同异常一分钟内只上报一次，并保留每会话五十条的原有上限。

## 同步模式

### 默认：增量轮询

`getRoomSnapshot` 未设置 `ROOM_SYNC_MODE` 或设置为 `poll` 时，默认在成功响应后五秒进行下一次串行轮询。变化量通过游标读取；默认心跳仍为三十秒。在线期限统一延长为三分钟，与 watch 的六十秒心跳配套，首页人数、房间名单和定时清理使用相同期限。

这种模式减少了重复历史、数据库读取和流量，但空闲时仍有约五秒一次的云函数调用，不能据此保证二十万次配额支持任意人数推广。

### 可启用：单连接通知＋增量读取

仅在 `getRoomSnapshot` 云函数环境变量中设置 `ROOM_SYNC_MODE=watch`。不需要给其他函数逐一配置该变量：订阅阶段在房间记录中启用通知标志，后续业务事务按该标志更新通知文档。

每个前台房间会话只监听自己的一个 `roomFeeds/{playerId}` 文档。通知仅包含版本、记录序号和状态，不含其他成员身份或账目。收到版本变化后合并突发通知，读取新增数据。静默时默认每六十秒进行心跳及校准。切后台关闭监听，回前台重新建立连接并校准。

静置间隔调整为六十秒后，四人一桌每小时的基础校准调用约为二百四十次（不含记分、初始化等调用）。通知遗漏时兜底校准最多等待约一分钟；断网时还会受到重试退避影响。直接切后台/关闭而未主动退出的玩家，在线状态最多保留约三分钟。全员失联时，关房条件为最后活动后三分钟在线期限再加五分钟空房等待，实际归档还受五分钟定时器调度影响；主动全员退出仍等待五分钟。

心跳只更新在线信息，不发布业务版本变化。通知连接失败时回退默认五秒增量轮询并在 Console 留下提示；普通请求失败采用指数退避，权限/身份明确失效时停止重试。

回退后自动尝试恢复 watch：从每次监听失败起，依次等待三十秒、六十秒、一百二十秒，之后每次五分钟；到期后借下一次成功的轮询重新登记订阅并建立监听，不额外并发请求快照。重连初始化期间仍保持五秒轮询，收到首个监听快照才恢复六十秒静置校准，并重置重连退避。初始化十秒无回调会关闭该连接，再退避重试。实际重试时刻受轮询周期、网络和请求失败退避影响。Console 出现“房间通知连接已恢复，已停止增量轮询”表示恢复成功。切后台、停止会话或切换房间会关闭连接并取消旧任务；回前台重新校准并尝试连接。服务端切换为 poll 时停止 watch 重试。

注意：官方配额制个人版文档列出的实时推送连接数为十个，每次 watch 占一个连接。先核对实际环境额度，再确认它能够覆盖推广人数；代码不自动升级套餐或购买连接数。通知和增量读取仍有资源消耗，并非免费通道。连接超限后回退会增加调用，必须监控。

### 其他可调整参数

若已有 `ROOM_POLL_MS=2000`，需要改为 `5000` 或移除覆盖值，才会使用新的五秒默认值。watch 正常时通知仍立即触发读取；轮询模式显示变化最多需要约五秒加网络耗时。

以下参数同样只配置在 `getRoomSnapshot`，前端读取服务器返回的策略，不需要为了调整参数重新发布前端。无效值自动使用默认值：

| 环境变量 | 默认值 | 允许范围（毫秒） |
| --- | ---: | --- |
| ROOM_POLL_MS | 5000 | 1000–5000 |
| ROOM_HEARTBEAT_MS | watch 为 60000，poll 为 30000 | 15000–60000 |
| ROOM_RECONCILE_MS | 60000，受心跳间隔限制 | 5000–60000，实际不会超过心跳间隔 |

范围限制配合三分钟在线期限与默认五秒轮询间隔，不允许配置零间隔形成请求风暴。失败重试按五、十、二十、三十秒退避，重复失败时带少量随机延迟。环境变量修改需要按平台流程重新部署生效。已有 `ROOM_HEARTBEAT_MS=30000` 或 `ROOM_RECONCILE_MS=30000` 会覆盖新默认值，若需六十秒，应改为 `60000` 或移除这两个覆盖项，保留 `ROOM_SYNC_MODE=watch`。

## 必须先完成的云端准备

1. 备份现有云函数与环境配置，记录当前版本，选择测试环境验证。
2. 新建集合 `requestLimits`，设置权限为 `docs/deployment/requestLimits.rules.json`；不允许客户端读取或写入。
3. 新建集合 `roomFeeds`，设置权限为 `docs/deployment/roomFeeds.rules.json`：仅当前身份所属文档可读，客户端不可写。不要设置为所有人可读写。即使暂用轮询，也建议先准备好集合与权限。
4. 核验以下索引。按照控制台支持的索引创建方式及缺失索引提示处理，避免重复创建：

| 集合 | 查询/排序字段 |
| --- | --- |
| rounds | roomId、roundIndex 升序、_id 升序 |
| rounds | roomId、roundIndex 降序 |
| rounds | roomId、createdAt 降序 |
| rounds | roomId、clientId |
| players | roomId、_id 升序 |
| players | openid、joinedAt 降序、_id 升序 |
| players | clientId、joinedAt 降序、_id 升序 |
| players | roomId、isOnline、lastSeenAt |
| rooms | status、nextCheckAt 升序、_id 升序 |
| rooms | status、_id 升序（旧房间缺少 nextCheckAt 的兼容查询） |
| rooms | roomCode |

`nextCheckAt` 缺失条件和按身份 OR 查询的索引支持需在实际云环境验证，索引创建完成后再放量。

5. 在项目根执行 `npm run prepare:cloud`。
6. 先部署 `settleRound`、`createRoom`、`joinRoom`、`leaveRoom`、`updatePlayer`、`updateRule`，再部署 `getRoomSnapshot`、`getMyRooms`、`autoCloseTimeout`。均上传完整函数目录并云端安装依赖，包含新的 `_shared/roomSync.js`。`getRoomQRCode` 与 `logError` 本次没有后端代码改动。
7. 保留 `autoCloseTimeout` 原每五分钟定时器。其运行超时应在云控制台设置为至少四十五秒，确保二十秒工作预算、查询与清理有余量。旧房间首次摘要补建可能比正常同步慢，应核验 `getRoomSnapshot`、`settleRound` 的实际超时配置与大历史场景。
8. 先以默认 `poll` 模式预览新版前端。旧前端不携带协议号，仍使用原完整分页接口；新前端显式请求协议 2，能兼容旧接口响应，但部署前端前仍应完成所有后端更新。
9. 确认规则、连接额度后，再按需要在 `getRoomSnapshot` 开启 `ROOM_SYNC_MODE=watch` 并重新部署使环境变量生效。检查 Console 无“通知连接不可用，已回退增量轮询”，并观察实际连接数和调用曲线。
10. 最后发布前端新版。Git 提交/推送、部署云函数、提交审核和发布仍是独立操作。

六十秒静置调整涉及公共在线期限与查询条件，需要重新部署以上九个函数（包括 `getMyRooms`），保证首页、房间、记分和清理对在线期限的判断一致。公共副本已在本地执行 `npm run prepare:cloud` 同步；完整上传并云端安装依赖即可。保留已有集合、权限、索引与定时器。

## 验证与实测边界

执行：

```bash
npm test -- --runInBand
npm run test:coverage -- --runInBand
npm run benchmark:sync
npm run check:banned
```

内存模拟中的 501 条历史房间，一轮静默同步对比：

| 指标 | 原协议 | 新协议 |
| --- | ---: | ---: |
| 云函数调用 | 6 | 1 |
| 数据库操作 | 20 | 2 |
| 响应字节 | 84481 | 765 |

该对比计量的是模拟请求，不是腾讯云最终计费口径；未包含心跳与其他业务。默认轮询下调用频率为响应后五秒。

并发正确性模拟为二十间房、每间四名玩家，共两千次提交尝试（每个操作重复两次）：新增一千笔，不重复入账，各房间序号连续、总分守恒。模拟器串行提交事务，不模拟真实数据库冲突重试、网络时延、服务限流及实时连接配额，不能将耗时作为线上吞吐承诺。

另用实际 `wx-server-sdk@2.6.3` 在无网络存根上检查缺失文档返回、`_openid` 通知归属字段、组合游标条件与 101 条分页参数。不能代替实际云端验收。

### 真机及测试环境验收

通知监听使用 `where({ _id: watchId, _openid: '{openid}' })`，身份占位符由云端解析。自定义安全规则要求查询显式包含归属条件，不能改回仅 `doc(watchId).watch()`。若遇到 `-402002` 且普通读取诊断为 `-502003`，先确认前端已包含此修复及集合规则已保存；不要放开所有人读取。此修复只需更新前端，不需重部署云函数。监听失败时每个连接最多进行一次普通读取诊断，不打印文档内容或身份值。

- 创建房间后能直接看到邀请框；二维码下载前有提示，慢网仍可关闭，失败重试不循环调用。
- 至少两台手机交替记分超过一百条，排行榜、历史、冷启动和已结束战绩一致。
- 制造“服务端已写入但响应丢失”的情况，同一编号最终只入账一次，待确认提示能自动或手动消除。
- watch 模式下，两人操作正常网络目标为一至两秒更新；静默时每位玩家约每六十秒调用一次同步函数，不应每五秒调用。该目标仍需真实环境测量。
- 断网触发回退后恢复网络，不退出房间也应能自动恢复 watch；恢复期间五秒轮询持续更新，恢复成功后不再高频轮询。检查反复失败按三十/六十/一百二十秒/五分钟退避，切后台后不保留重试任务。
- 把通知权限临时设为拒绝以验证回退；验证当前用户不能读取另一用户的通知文档，所有客户端均不能写通知。验证完立即恢复预定规则。
- 打开历史、切后台、断网后他人继续记分，再回前台，仍能补齐数据且不重复累计。
- 全员退出/直接切后台按原窗口归档，至少一人前台长时间不记分时不误关；批量归档有积压时看 `more` 和 `failures`。
- 检查请求量、数据库操作、连接数、错误率及实际同步时延后，再决定推广范围、资源预算和是否开启超限不停服；本次没有更改计费设置。

## 回退方式

先将 `getRoomSnapshot` 的 `ROOM_SYNC_MODE` 改为 `poll` 并部署，前端收到策略后关闭监听并使用增量轮询。无需删除账目、玩家、摘要或通知集合。

后端尽量保留本次支持新旧协议的版本；如需整体回退代码，应协调前端一起回退，并保留原始 rounds。不要只回退记分事务后仍长期使用旧的总分摘要。若旧版本曾写入而使摘要序号落后，新协议会重新核对，但不应依靠这种兼容兜底作为长期混用方案。
